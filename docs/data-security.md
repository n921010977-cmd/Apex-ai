# Безопасность хранения данных — Vertlix AI

> **Важно про стек.** В проекте используется **PostgreSQL через Supabase**
> (`@supabase/supabase-js` + `@supabase/ssr`), а **не Prisma**. Файл
> `schema.prisma` в корне — «мёртвый»: пакета `prisma` нет в зависимостях и он
> нигде не импортируется. Его стоит либо удалить, либо, если планируется переход
> на Prisma, довести миграцию до конца. Ниже всё описано под реальный стек
> (Supabase). Практики универсальны — при переезде на Prisma переносятся 1:1.

---

## 1. Пароли — bcrypt ✅ (уже сделано)

- Хеширование: **bcryptjs, cost factor 12** — везде, где создаётся/меняется пароль
  (`register`, `reset-password`, `user/password`, проверка в `auth.ts`).
- В БД хранится только колонка `password_hash`; открытый пароль не пишется никуда
  и не логируется.
- OAuth-пользователи (Google/GitHub) `password_hash` не имеют — вход только через
  провайдера; смена пароля для них требует установки нового без «текущего».

Ничего добавлять не нужно. При переходе на аргумент из ТЗ «добавь bcrypt» —
он уже интегрирован корректно.

## 2. Безопасное хранение токенов ✅ (уже сделано)

- **Сессии**: NextAuth v5, стратегия **JWT** — сессия подписывается
  `NEXTAUTH_SECRET`, в БД не хранится. На проде cookie автоматически `Secure` +
  `HttpOnly` + `SameSite=Lax` (и префикс `__Secure-`).
- **Токены сброса пароля**: **stateless HMAC-SHA256** (`src/lib/reset-token.ts`) —
  подписываются секретом, TTL 1 час, сверка timing-safe. В БД **не хранятся** →
  нечего украсть из дампа.
- **API-ключи** (таблица `api_keys`): хранится только `key_hash`, не сам ключ.

Принцип: **секреты либо не хранятся (stateless), либо хранятся только в виде
хеша.** Обратимо расшифровываемые токены — через раздел 3.

## 3. Шифрование чувствительных данных (добавлено)

Новый модуль `src/lib/crypto/encryption.ts` — **AES-256-GCM** (аутентифицированное
шифрование) для полей, которые должны быть нечитаемы прямо из дампа БД, но которые
нужно уметь расшифровать обратно: OAuth refresh-токены, секреты 2FA, сторонние
API-ключи, отдельные PII по требованию договора.

```ts
import { encrypt, decrypt, encryptIfConfigured } from "@/lib/crypto/encryption";

const stored = encrypt(refreshToken);   // "v1:<iv>:<tag>:<ciphertext>"
const back   = decrypt(stored);         // бросает, если подделано/не тот ключ
```

- Ключ: `DATA_ENCRYPTION_KEY` — 32 байта, `openssl rand -base64 32`.
- Формат версионирован (`v1:`) → возможна ротация алгоритма/ключа.
- `encryptIfConfigured()` — no-op без ключа (безопасная деградация в dev).
- Проверено: round-trip, отклонение подделки (GCM auth tag), недетерминизм (random IV).

> Пароли этим **не** шифруются — для них односторонний bcrypt (раздел 1). Симметричное
> шифрование только для данных, которые реально нужно возвращать в открытый вид.

## 4. Защита пользовательской информации

**Уровень приложения (сделано):**
- Каждый data-роут проверяет сессию и фильтрует запросы по `user_id` / `owner_id`
  (нет доступа к чужим данным).
- Экспорт данных отдаёт профиль **явным списком колонок** — `password_hash`
  физически не может попасть в выгрузку (проверено).
- Rate limiting по реальному IP (`CF-Connecting-IP` за Cloudflare).

**Уровень БД — Row Level Security (требует внимания):**
Миграции определяют RLS-политики, НО приложение ходит в Supabase с **ANON-ключом
поверх сессии NextAuth**, а не через Supabase Auth. Значит `auth.uid()` в políтиках
будет `NULL`, и наивное включение RLS `USING (auth.uid() = user_id)` **заблокирует
всё**. Варианты:
1. **Серверный доступ через service-role ключ** + ручная фильтрация по `user_id`
   (уже есть в коде) — тогда RLS выступает как «defense in depth» с политиками,
   рассчитанными на service-role bypass.
2. Выдавать Supabase-совместимый JWT, чтобы `auth.uid()` заполнялся.

Не включай RLS «в лоб» до выбора модели — сломаешь прод. Подробности и рекомендация
— в обсуждении безопасности API.

## 5. GDPR — лучшие практики (добавлено)

| Право (GDPR) | Реализация |
|---|---|
| **Art. 15/20 — доступ и переносимость** | `GET /api/user/export` — скачивает весь профиль и данные пользователя одним JSON-вложением (без секретов). ✅ |
| **Art. 17 — право на забвение** | `DELETE /api/user` — удаляет аккаунт и все связанные данные по всем таблицам, затем строку `users`. ✅ |
| **Art. 32 — безопасность обработки** | bcrypt, HMAC-токены, AES-256-GCM, HTTPS/HSTS, security headers, rate limiting. ✅ |
| **Art. 5 — минимизация** | Собираем только email/имя/аватар + контент, который создаёт сам пользователь. |

**Что ещё стоит добавить по GDPR (вне кода / по мере роста):**
- **Кнопки в UI** для экспорта и удаления аккаунта (эндпоинты готовы — подключить
  в `Настройки → Безопасность`).
- **Политика конфиденциальности и Cookie-consent** (у вас уже есть `/legal` — сверьте
  содержимое с реальной обработкой данных и списком под-обработчиков: Supabase,
  Anthropic, Vercel, Cloudflare, Resend).
- **Соглашения об обработке данных (DPA)** с под-обработчиками.
- **Политика хранения** (retention): срок жизни `activity_logs`, автоочистка.
- **Журнал согласий** пользователя (opt-in на маркетинг отдельно от сервиса).
- **Уведомление об утечке** ≤ 72 ч — процесс, не код.
