# План защиты персональных данных — Vertlix AI

**Роль документа:** практический план защиты ПДн, привязанный к фактической
кодовой базе, а не к абстрактному шаблону. Каждый пункт помечен реальным
статусом:

- ✅ **Реализовано** — уже есть в коде, указан файл.
- ⚠️ **Частично / требует настройки** — код есть, но нужно действие при деплое.
- ❌ **Пробел** — отсутствует, нужно сделать до запуска.

**Архитектура:** Next.js (frontend + API routes) · PostgreSQL (Supabase) ·
NextAuth (аутентификация) · Vercel (хостинг приложения) + VPS · Anthropic (AI) ·
LemonSqueezy (платежи) · Resend (почта) · PostHog (аналитика).

## 🔴 Критичные находки (исправить ДО запуска)

Найдены при аудите текущего кода — оба закрываются в несколько строк:

### F-1. Захардкоженный секрет-фолбэк (высокий риск)
`src/auth.config.ts:27`, `src/lib/verify-token.ts:11`, `src/lib/reset-token.ts:11`
подставляют **публично известную строку**, если переменная окружения не задана:

```ts
secret: process.env.NEXTAUTH_SECRET ?? "apex-ai-dev-secret-change-in-production"
// verify/reset: process.env.NEXTAUTH_SECRET || ... || "vertlix-dev-secret-change-me"
```

**Угроза:** если в проде `NEXTAUTH_SECRET` не задан, приложение молча работает на
секрете, который знает любой, кто видел исходники. Это позволяет **подделать
session-JWT, токены подтверждения email и сброса пароля** — то есть войти под
любым пользователем и сбросить чужой пароль. Прод-гварда, который бы падал при
отсутствии секрета, сейчас нет.

**Фикс:** падать при старте в проде, если секрет не задан (не подставлять фолбэк):
```ts
function requireSecret() {
  const s = process.env.NEXTAUTH_SECRET ?? process.env.AUTH_SECRET;
  if (!s) {
    if (process.env.NODE_ENV === "production")
      throw new Error("NEXTAUTH_SECRET is required in production");
    return "dev-only-secret"; // фолбэк допустим ТОЛЬКО в dev
  }
  return s;
}
```
Секрет генерировать `openssl rand -base64 32`, хранить только в env хостинга.

### F-2. Ссылка сброса пароля пишется в лог (средний риск)
`src/app/api/auth/forgot-password/route.ts:46` — если `RESEND_API_KEY` не задан,
ссылка сброса (с валидным токеном) уходит в `console.log`. В проде без настроенной
почты **токены сброса утекают в логи сервера**.

**Фикс:** логировать ссылку только при `NODE_ENV !== "production"`; в проде без
почты — отдавать ошибку конфигурации, а не писать токен в лог.

## 1. Защита пользователей

| Мера | Статус | Где / что делать |
|---|---|---|
| Хэш паролей | ✅ | `bcrypt`, 12 раундов — `register`, `reset-password`, `user/password`. Пароли в открытом виде не хранятся. |
| Резервные коды 2FA | ✅ | Хэшируются `bcrypt` — `src/lib/two-factor.ts:45`. |
| Шифрование 2FA-секретов | ✅ | AES-256-GCM — `src/lib/crypto/encryption.ts`, хранится `two_fa_secret_enc`. |
| Двухфакторная авторизация (TOTP) | ✅ | Полный флоу — `src/lib/two-factor.ts`, гейт в `authorize()` `src/auth.ts:152`. |
| Вход по passkey (WebAuthn) | ✅ | `src/auth.ts` — отдельный provider, проверка подписи на сервере. |
| Защита сессий (JWT) | ⚠️ | NextAuth `strategy: "jwt"`, `maxAge: 30 дней`, cookie `httpOnly`+`SameSite`. **Действие:** задать сильный `NEXTAUTH_SECRET` (см. F-1); рассмотреть сокращение `maxAge` до 7–14 дней для чувствительного продукта. |
| Брутфорс-защита логина | ✅ | `authLimiter` в `authorize()` — 10 попыток / 15 мин по IP+email. |
| Сброс/подтверждение по токену | ⚠️ | Подписанные токены с TTL 1ч. **Действие:** см. F-1 (секрет) и F-2 (лог). |

**Рекомендации на будущее:** миграция bcrypt → **Argon2id** (устойчивее к GPU) при
следующем ротировании — версионировать хэш (`$argon2id$…`), проверять оба формата
при логине, перехэшировать при успешном входе. Не обязательно к запуску, bcrypt(12)
приемлем.

## 2. Защита базы данных

| Мера | Статус | Где / что делать |
|---|---|---|
| Изоляция данных (RLS) | ✅ | `009_rls_lockdown.sql` — RLS включён на всех таблицах, anon-ключу доступ запрещён; сервер ходит service-role ключом, авторизация — скоупингом по `user_id`/`organization_id` в API. |
| Отдельный пользователь БД с мин. правами | ⚠️ | Supabase даёт `anon` (заблокирован RLS) и `service_role`. **Для VPS-Postgres:** завести отдельную роль приложения только с `SELECT/INSERT/UPDATE/DELETE` на нужные таблицы, без `SUPERUSER`/`CREATEROLE`/DDL. Не использовать `postgres`-суперюзера в приложении. |
| Шифрование бэкапов | ❌ | **Действие:** бэкапы шифровать (Supabase PITR шифрует at-rest; для VPS — `pg_dump | age -r <key>` или `gpg`, ключ хранить отдельно от бэкапов). |
| Регулярные backup | ⚠️ | Supabase: включить ежедневные бэкапы + PITR на платном плане. VPS: cron `pg_dump`, ретенция 7–30 дней, **проверять восстановление** (бэкап без теста восстановления = нет бэкапа). |
| Аудит запросов | ⚠️ | В приложении каждый доступ скоупится по `user_id` (см. RLS-комментарий). **Действие для VPS:** включить `pgaudit` или `log_statement='ddl'` + логирование медленных/ошибочных запросов. |
| Шифрование канала к БД | ⚠️ | **Действие:** `sslmode=require` (лучше `verify-full`) в строке подключения к Postgres на VPS. |
| Шифрование чувствительных полей | ✅ | AES-256-GCM для 2FA-секретов. Расширить на будущие секреты через тот же `encryption.ts`. |

## 5. Логи (что НЕЛЬЗЯ сохранять)

| Правило | Статус | Комментарий |
|---|---|---|
| Не логировать пароли | ✅ | Пароли нигде не пишутся в лог; в БД — только bcrypt-хэш. |
| Не логировать токены сессий | ✅ | JWT/session-токены не выводятся. |
| Не логировать токены сброса/подтверждения | ⚠️❌ | **F-2:** `forgot-password` пишет ссылку сброса в `console.log` в фолбэк-ветке. Исправить (см. выше). |
| Не логировать платёжные данные | ✅ | Карты обрабатывает LemonSqueezy (merchant of record) — приложение их не видит и не хранит. |
| Не логировать секреты/API-ключи | ✅ | Ключи не выводятся; ошибки провайдеров логируются без тела запроса. |
| PII в логах | ⚠️ | Email может попадать в диагностические логи. **Действие:** для прод-логгера — маскировать email (`u***@dom.com`), не логировать содержимое проектов/AI-запросов. |

**Общее правило логирования:** уровень `info` — без чувствительных данных;
структурированные логи; ретенция ограничена (напр. 30 дней); доступ к логам —
только у ответственных.
